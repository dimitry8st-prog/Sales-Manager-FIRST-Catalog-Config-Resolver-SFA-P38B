ТЕХНИЧЕСКОЕ ЗАДАНИЕ F1-10 R1
Sales Manager FIRST — проверка результата квалификации найденного клиента
Исполнитель: не назначен. При выдаче координатор укажет исполнителя отдельно.

1. ЧТО НУЖНО СДЕЛАТЬ

Написать один небольшой модуль Python, который проверяет согласованность и актуальность уже полученных сведений о потенциальном покупателе. Модуль получает кандидата, результат исследования и серверную конфигурацию; возвращает одно из трёх решений: можно передать в подготовку, кандидат не соответствует, нужна дополнительная проверка.

Он не ищет компании, не открывает сайты, не вызывает модель и не отправляет письма. Он также не доказывает истинность текста сайта или качество исследования: это ответственность будущего доверенного исследовательского адаптера и его отдельной приёмки. Здесь проверяется именно граница между результатом такого исследования и следующим этапом продавца.

Почему это нужно: существующий process_discover проверяет область результата и передаёт найденный lead на ingest. Синтаксически правильный адрес и URL сами по себе не доказывают, что найден покупатель нужного предложения. Само наличие этих полей не различает покупательскую потребность и предложение поставщика. Новый модуль должен требовать явно связанное, свежее исследование и отличать отрицательный вывод от отсутствующих знаний.

Не считать любую компанию-поставщика неподходящим покупателем. Компания может продавать свои услуги и одновременно покупать наше предложение. Отклоняется только подтверждённый результат PROVIDER_ONLY: исследование установило, что найдено предложение поставщика вместо свидетельства покупательской потребности. При неопределённости возвращается NEEDS_REVIEW. Отказ по одному кандидату не означает отсутствие рынка и не завершает кампанию.

4. ОБЩИЕ ПРАВИЛА ТИПОВ

identifier — строка, fullmatch ASCII regex [A-Za-z0-9][A-Za-z0-9_.:-]{0,127}.
text — строка, не пустая после strip(); возвращаемый текст не изменять.
uuid — строка канонического UUID в нижнем регистре, то есть str(UUID(value)) == value.
email — непустая строка; нормализовать strip().lower(), затем fullmatch regex [^\s@]+@[^\s@]+\.[^\s@]+. Это только синтаксис, не проверка доставляемости.
url — непустая строка без внешних пробелов; urlsplit должен дать scheme ровно https и непустой hostname; username/password запрещены. Сеть не использовать. Сохранять исходную строку и сравнивать URL точно, не пытаться установить эквивалентность разных ссылок.
timestamp — непустая ISO8601 строка. Разбирать datetime.fromisoformat, заменив только конечный Z на +00:00; обязательны tzinfo и определённый utcoffset. Сравнивать по моменту времени.
sha256 — строка ровно 64 символа lowercase hex.
seconds — Python int >0, bool запрещён. Никаких float/NaN/бесконечности.

now должен быть datetime с часовым поясом и определённым utcoffset. Неподходящий тип или naive datetime — ошибка. Контейнеры — dict/list согласно схеме; неизвестные поля запрещены. Нельзя исправлять вход угадыванием отсутствующих значений.

5. ЧЕТЫРЕ СХЕМЫ ВХОДА

candidate — dict ровно с полями:
  schema_version: "FIRST_DISCOVERY_CANDIDATE_V1"
  candidate_id: identifier
  client_id: identifier
  runtime_campaign_id: uuid
  company_name: text
  contact_email: email
  source_url: url

binding — dict ровно с полями:
  schema_version: "FIRST_QUALIFICATION_BINDING_V1"
  client_id: identifier
  runtime_campaign_id: uuid
  offer_id: identifier
  binding_version: identifier

Это специальная проекция серверной конфигурации для данного компонента. Она не является форматом Make и не заменяет FIRST_BINDING_V1 из F1-05. Будущий интегратор построит её явно. Не извлекать binding из письма клиента, raw Make response или текста модели.

policy — dict ровно с полями:
  schema_version: "FIRST_QUALIFICATION_POLICY_V1"
  policy_version: identifier
  max_source_age_seconds: seconds
  max_assessment_age_seconds: seconds

Возраст источника и исследования задаётся конфигурацией. Не зашивать отрасль, страну, язык или вид товара в код. Этот компонент не определяет языки переписки: EN/RU и расширяемые языковые пакеты остаются действующим scope FIRST.

assessment — dict ровно с полями:
  schema_version: "FIRST_DISCOVERY_ASSESSMENT_V1"
  assessment_id: identifier
  assessment_version: identifier
  company_name: text
  contact_email: email
  binding_version: identifier
  candidate_id: identifier
  client_id: identifier
  runtime_campaign_id: uuid
  offer_id: identifier
  source_url: url
  source_content_sha256: sha256
  source_observed_at: timestamp
  checked_at: timestamp
  source_kind: "PRIMARY" либо "OTHER"
  source_state: "LIVE", "UNAVAILABLE" либо "UNKNOWN"
  buyer_role: "BUYER", "PROVIDER_ONLY" либо "UNKNOWN"
  offer_fit: "MATCH", "NO_MATCH" либо "UNKNOWN"
  contact_association: "CONFIRMED" либо "UNCONFIRMED"
  evidence_refs: непустой list уникальных text

assessment должен поступать только от будущего доверенного адаптера исследования. Этот модуль не принимает поле trusted=true, auth=true или verified=true и не превращает такую декларацию в доверие. Сведения об аутентификации источника, фактическом содержимом и независимой приёмке исследователя хранятся вне этого модуля. evidence_refs и hash дают прослеживаемость, но сами по себе не доказывают качество исследования.

6. СВЯЗЬ ВХОДОВ И ВРЕМЯ

Обязательно точное равенство:
- candidate.client_id == assessment.client_id == binding.client_id;
- candidate.runtime_campaign_id == assessment.runtime_campaign_id == binding.runtime_campaign_id;
- candidate.candidate_id == assessment.candidate_id;
- assessment.offer_id == binding.offer_id;
- assessment.binding_version == binding.binding_version;
- assessment.company_name == candidate.company_name: точное сравнение исходных строк, без strip/casefold/Unicode-нормализации;
- нормализованный assessment.contact_email == нормализованный candidate.contact_email: оба значения проверяются по типу email и приводятся через strip().lower().
- candidate.source_url == assessment.source_url.

Нельзя подменять runtime_campaign_id внешним make_campaign_id. При несовпадении scope/source/contact/company/version возвращать соответствующую ошибку, а не пытаться перепривязать сведения. Нельзя повторно использовать старое исследование после изменения версии binding, имени компании или контактного email, сохранив лишь прежний candidate_id. Совпадение этих полей доказывает только согласованность входов, не достоверность исследования. Изменение любых коммерчески значимых условий binding требует новой binding_version на стороне доверенного сервера; этот модуль не получает полный binding и не может обнаружить неотражённое в версии изменение условий.

source_observed_at <= checked_at <= now. Будущее время и обратный порядок — INVALID_TIME. Возраст source = now - source_observed_at, возраст assessment = now - checked_at. Свежесть сохраняется при age <= соответствующего лимита; ровно на границе ещё свежо. Превышение лимита — не ошибка формата, а NEEDS_REVIEW со специальной причиной.

7. ТОЧНЫЙ АЛГОРИТМ РЕШЕНИЯ

Сначала проверить типы, схемы, значения, scope и порядок времени. На некорректных данных не формировать успешный результат.

Затем проверить качество и свежесть основания в следующем порядке. Собрать все применимые reason_codes, сохраняя этот порядок:
  SOURCE_STALE — возраст источника превышает лимит;
  ASSESSMENT_STALE — возраст исследования превышает лимит;
  SOURCE_NOT_PRIMARY — source_kind не PRIMARY;
  SOURCE_NOT_LIVE — source_state не LIVE.
Если список непустой, вернуть NEEDS_REVIEW. Устаревший или неподтверждённый источник не даёт ни положительной квалификации, ни окончательного отрицательного вывода о кандидате.

Если основание свежее, PRIMARY и LIVE, проверить подтверждённые отрицательные признаки. Собрать по порядку:
  PROVIDER_ONLY — buyer_role == PROVIDER_ONLY;
  OFFER_NOT_MATCHED — offer_fit == NO_MATCH.
Если список непустой, вернуть NOT_QUALIFIED. Это касается только данного candidate/offer/assessment, не общего рынка. Остальные неопределённые поля не отменяют уже определённое отрицательное основание; например свежий NO_MATCH достаточен, даже если контакт ещё не подтверждён.

Если отрицательных признаков нет, собрать по порядку:
  BUYER_ROLE_UNKNOWN — buyer_role == UNKNOWN;
  OFFER_FIT_UNKNOWN — offer_fit == UNKNOWN;
  CONTACT_UNCONFIRMED — contact_association == UNCONFIRMED.
Если список непустой, вернуть NEEDS_REVIEW.

Если ни одно условие выше не сработало, вернуть QUALIFIED_FOR_PREPARATION с reason_codes ["QUALIFICATION_INPUTS_SUFFICIENT"]. Такое решение означает, что согласованные свежие структурированные сведения разрешают следующий этап подготовки. Оно не равно SEND_READY, проверке Hunter, фактической отправке, наличию согласия на коммуникацию или коммерческому успеху.

8. СХЕМА ВЫХОДА

Всегда возвращать dict ровно с полями:
  schema_version: "FIRST_QUALIFICATION_RESULT_V1"
  verdict: "QUALIFIED_FOR_PREPARATION", "NOT_QUALIFIED" или "NEEDS_REVIEW"
  reason_codes: list строк согласно алгоритму
  candidate_id: candidate.candidate_id
  client_id: binding.client_id
  runtime_campaign_id: binding.runtime_campaign_id
  offer_id: binding.offer_id
  binding_version: binding.binding_version
  policy_version: policy.policy_version
  assessment_id: assessment.assessment_id
  assessment_version: assessment.assessment_version
  contact_email: нормализованный candidate.contact_email
  source_url: исходный candidate.source_url
  source_content_sha256: assessment.source_content_sha256
  source_observed_at: ISO UTC с суффиксом +00:00
  checked_at: ISO UTC с суффиксом +00:00
  evaluated_at: now как ISO UTC с суффиксом +00:00
  evidence_refs: независимая копия assessment.evidence_refs

Все вложенные mutable-объекты результата независимы от входов. Никаких hidden side effects, дополнительного свойства approved=true, live_enabled или прав отправки.

9. ОШИБКИ И ПОРЯДОК ПРОВЕРКИ

QualificationError.code:
  INVALID_INPUT — базовый тип аргумента или now некорректен;
  INVALID_SCHEMA — schema_version/набор ключей не соответствует;
  INVALID_IDENTITY — неверный identifier/UUID;
  INVALID_CANDIDATE — company_name, contact_email или candidate.source_url некорректны;
  INVALID_POLICY — лимиты возраста не положительные int;
  INVALID_ASSESSMENT — enum, hash, assessment.source_url, assessment.company_name, assessment.contact_email или evidence_refs некорректны;
  SCOPE_MISMATCH — несовпадение client/campaign/candidate/offer;
  BINDING_VERSION_MISMATCH — assessment.binding_version не равна binding.binding_version;
  COMPANY_SCOPE_MISMATCH — assessment.company_name не равна candidate.company_name;
  CONTACT_SCOPE_MISMATCH — нормализованные assessment.contact_email и candidate.contact_email не равны;
  SOURCE_MISMATCH — два корректных source_url различаются;
  INVALID_TIME — разбор даты, отсутствие timezone, будущее или неверный порядок.

Проверять группы в указанном порядке. Все schema сначала, затем идентификаторы всех объектов и остальные группы. Внутри одной группы порядок может быть выбран автором, но остаётся детерминированным. Приёмочные negative-примеры ниже содержат одну ошибку. Никакие KeyError/TypeError/AttributeError/ValueError парсера не должны случайно выходить наружу при повреждённом входе. Не ловить BaseException. str(error) не должен содержать email, URL, body, токен или входной объект.

11. ОБЯЗАТЕЛЬНЫЕ ТЕСТЫ

Использовать unittest и независимые fixtures. Минимальная матрица:
- полный положительный пример и нормализация email;
- каждая ветка enum, включая UNKNOWN и PROVIDER_ONLY;
- компания с произвольным названием/предложением получает тот же алгоритм: никакого жёсткого отраслевого фильтра;
- порядок reason_codes при нескольких причинах;
- stale/other/non-live основания имеют приоритет над отрицательными оценками;
- свежий NO_MATCH не превращается в «рынок исчерпан»;
- точная граница max age и превышение на одну секунду;
- одинаковый момент с разными UTC offset; naive и будущая дата; source_observed_at после checked_at;
- чужой client/campaign/candidate/offer; разные source_url;
- смена candidate.contact_email при прежнем assessment CONFIRMED -> CONTACT_SCOPE_MISMATCH; различие только регистра/внешних пробелов email после нормализации допустимо;
- смена company_name при прежнем candidate_id -> COMPANY_SCOPE_MISMATCH; сравнение имени точное;
- новая binding.binding_version при прежнем assessment MATCH -> BINDING_VERSION_MISMATCH;
- несколько несовпадений одновременно: SCOPE_MISMATCH раньше BINDING_VERSION_MISMATCH, затем COMPANY_SCOPE_MISMATCH, затем CONTACT_SCOPE_MISMATCH, затем SOURCE_MISMATCH;
- неверные типы, schema, missing/extra поля; bool вместо лимита; duplicate/пустые evidence_refs;
- body-подобная строка или auth=true не создают полномочий;
- вход не меняется; результат не разделяет mutable evidence_refs с входом;
- одинаковый вход и now дают одинаковый результат;
- ошибки не выводят sentinel с имитацией секрета;
- импорт и все тесты не требуют psycopg, сети, БД, переменных окружения или внешних сервисов.

Не подменять qualify_candidate в собственных тестах. Тест должен вызывать реальную функцию и проверять точные verdict/reasons/error code. Не удалять проверки ради зелёного результата и не менять frozen source.

12. КАК ЗАПУСТИТЬ И СДАВАТЬ

Из корня пакета:
  python3 CHECK_PACKAGE.py
  python3 RUN_NEW_TASK.py

RUN_NEW_TASK.py запускает только тесты данного нового задания в изолированной среде, как описано в приложенном руководстве. Это не проверка всех новых модулей и не устранение известных ошибок baseline. Для прямого локального запуска из source/:
  python3 -m unittest discover -s tests -p test_discovery_qualification.py -v
  python3 -m py_compile sales_discovery_qualification.py tests/test_discovery_qualification.py

Записать настоящие stdout/stderr и exitcode. Python3.12 обязателен; на Windows допустим py -3.12 с фиксацией фактической команды. Не заявлять macOS PASS по запуску на Linux/Windows. Для macOS модуль остаётся переносимым благодаря stdlib; фактический запуск подтверждается отдельно.

Чекпойнты:
CP0 — проверить базу, allowlist и отсутствие пересекающегося назначения.
CP1 — сверить сигнатуру, четыре схемы и тестовую матрицу; вопросы по существенному изменению направить координатору до правки контракта.
CP2 — модуль и реальные тесты, перечень оставшихся проблем.
CP3 — полный RETURN ZIP, статус READY_FOR_REVIEW.
После возврата независимый reviewer проверяет; отдельный инженер интегрирует; конечную сборку принимает отдельный reviewer. Автор не выставляет себе независимый PASS.

13. СОСТАВ ОДНОГО ВОЗВРАТА

Один архив с одним корнем F1-10_RETURN_R1:
- TASK_REPORT.md: project_id/task_id/return revision, исполнитель, exact base, фактическая среда, выполненное, ограничения, инструкция будущего подключения;
- source/ — только разрешённые новые файлы;
- patch.diff — git-compatible patch относительно чистой базы, проверенный в отдельной копии;
- RETURN_MANIFEST.json — базовый SHA256, task_id F1-10, return_revision, новые пути и SHA256 каждого файла;
- TEST_RESULTS.md — требование -> тест/команда -> log -> exitcode -> PASS/FAIL/NOT_RUN;
- logs/ — настоящие журналы;
- LIMITATIONS.md — явные непроверенные условия и зависимости интеграции.

Не включать credentials, .git, venv, __pycache__ или реальные данные клиентов. Не присылать только сообщение «готово» вместо файлов. Не выдумывать момент получения/начала/возврата: если он неизвестен, указать UNKNOWN. После каждого возврата и попытки интеграции координатор обязан дать владельцу отчёт главного инженера, включая нулевое изменение индекса.

14. МЕСТО В АРХИТЕКТУРЕ И ГРАНИЦА ГОТОВНОСТИ

Будущий путь: Make discovery FOUND -> доверенный адаптер исследования и серверный binding -> qualify_candidate -> разрешённая дальнейшая подготовка. Если вернулся NEEDS_REVIEW, сообщение о необходимости проверки не превращается в отказ по всему рынку. Если NOT_QUALIFIED, отклоняется только этот candidate для данного offer/assessment. Сохранение результата, маршрутизация следующего кандидата и изменение campaign state будут подключены отдельно.

Доверенный адаптер исследования ещё не реализуется здесь и не заменяется утверждением внутри JSON. Перед production потребуются доказательства его происхождения, семантической точности и реального positive sales-chain. Вызов Hunter и подготовка материалов сохраняют свои отдельные проверки.

Задание вносит часть FG03, но не закрывает этот gate само по себе. Не снимает NO_OUTBOUND, не разрешает реальный запуск и не увеличивает индекс только фактом сдачи. Принятые company/product/email/география вводятся позднее при подготовке пилота; сейчас synthetic данные позволяют выполнить всё задание без этих сведений.
